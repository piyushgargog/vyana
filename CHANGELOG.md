# Changelog

All notable changes to Vyana are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Removed
- Removed the medicine basket, lab price comparison, hospital OPD info and PM-JAY list endpoints, with their contracts, mocks, hooks and tests (the screens use plain links now).
- Removed the web agent vendor integration completely: code, tests, scripts, environment variables and the privacy page entry.

### Added
- When a plan's daily AI limit is used up, AI features answer with the usual 'try again later' message until midnight (India time).

### Changed
- Web: appointment booking and the admin hospitals tab no longer look up OPD timings with an agent; they show an "Open the hospital's own website" link when the hospital has a saved https address (issue #339).
- Phone: PM-JAY hospitals (schemes screen and SOS) and OPD timings in appointment booking no longer use an agent. PM-JAY shows a link to the official portal with a plain line that eligibility and the hospital list are checked there; booking shows an "Open the hospital's own website" link when the hospital has a saved https address (issue #339).
- Trend chart, QR code and phone screens now read the shared design tokens (issue #365): the trend chart's second series changes colour, and the phone screens change look slightly, to match the web theme.
- Phone navigation pass (U2): sheets now show a grabber and the Android sheet closes by tapping the dimmed area behind it, not only the close button. Haptics land on the moments that confirm something — a success tap when a dose is marked taken and when a share link is copied, and the warning tap when an SOS starts — never on ordinary taps. The hospital picker in appointment booking gets a real search field (search keyboard, clear button, results under it, a "no match" line).
### Fixed
- The live check of the care plan adds a condition the demo patient does not have yet (a condition can exist only once per patient since migration 0020) and deletes it again.
- Sign-up errors no longer show the provider's text on web and phone (issue #405): every failure says "We could not create your account. Check your details and try again." (password-too-short and invalid-email keep their own lines), and an address that already has an account gets the same "Check your inbox" screen as a new one, so a visitor cannot tell whether an email is registered.
- The chat and care text renderer can no longer be slowed down by a message made of thousands of `[` (CodeQL alert 53, polynomial regular expression): a link label cannot contain a bracket and label and address are length-capped.
- The welcome screen shows from the first frame: the native splash and the welcome logo are the same size (104), the card is solid, and the splash is hidden after 2.5 s at the latest, so the app can no longer sit on an empty screen.
- Error wording pass (U5): no screen says "Something went wrong" any more — the basket, care plan, prescription, report and upload errors now say what could not be loaded or finished and what to do next, and the phone's start-up loading screen says "Loading your Vyana…" under its spinner instead of showing a bare spinner. A scan test keeps the old phrase out of the apps.

### Added
- Care agent rules (issue #341): three pure functions in `apps/web/lib/server/agent/rules.ts` decide when to suggest a refill, a lab re-check or a talk about missed doses; no database or model is involved and the wording is fixed.
- Signup now handles email confirmation on web and mobile: a signup that returns no session shows a “Check your inbox” state with the address, a note that the link expires, and a resend button with a 60-second cooldown. Confirmation links use one explicit landing page (`/auth/confirmed`) that sends a signed-in person to DPDP consent and everyone else to sign in.
- One council registration can be verified for only one doctor account, enforced by the database itself (issue #360): migration 0022 adds a partial unique index on `doctors` over the normalised registration number and council for verified rows, so two approvals of the same number at the same moment can no longer both save — the second save is refused by the database, and the admin approval answers "This registration is already linked to another account." instead of a server error. Applying the migration stops with the offending keys named if verified doctors already share a registration.
- A fixed-sentence trend helper for device readings (`computeTrend`, `describeTrend` in `@vyana/shared`): the 7-day average against the week before for steps, resting heart rate and sleep, with five fixed sentences, no model and no judging words.
- README "Screens" section with the home page at desktop (1366 px) and phone (390 px) sizes in `docs/images/`, plus `docs/images/capture-screens.mjs` — one command that captures the remaining app screens (Today, Ask Vyana, scan result, care plan, interactions, blood, SOS) at both sizes once it is given the demo patient's login, and the checklist every image must pass (demo data only, no keys or server addresses, under 300 KB).
- Plans, limits and a waitlist, tables only (issue #301, migration 0016): `plans` holds the three plans and their placeholder limits (free: 30 AI calls a day, 1 profile, at most 3 open care-agent suggestions; family: 150 a day, 5 profiles, caregivers, no suggestion limit; clinic: no limits yet), `user_plans` says which plan each profile is on — every new profile starts on free by trigger, everyone already here was backfilled — and `current_plan()` hands a signed-in user their own plan with its limits (`getCurrentPlan`, `useCurrentPlan`). The `waitlist` table has no direct access at all; `join_waitlist(email, plan_id, note)` is the only way in (address checked, length-capped at 254 characters and lower-cased, note capped at 200 characters; a signed-in caller may join 5 times an hour, counted by account, and anonymous joins are capped as a whole — 30 an hour — so the form cannot be flooded by varying the address; the function answers only whether the address is new to the plan, never the stored row), through `joinWaitlist` and `useJoinWaitlist`.
- A load-test suite for the hot routes (issue #303): `scripts/load/` holds a k6 script with the six scenarios (dashboard reads, `/api/me`, blood search, care plan and assistant chat on the mock model, the public share page) ramping 10 → 50 → 100 virtual users, and a README with the exact commands. It runs on a local or staging build only — the script refuses a live-looking address.
- The missed-dose scan has an index of its own (issue #303, migration 0018): `dose_logs (status, scheduled_for)`, so the every-15-minutes cron route reads its window directly — on 104k synthetic dose logs a day-window count went from 2.9 ms to 0.36 ms, and the broad status reads are index-only scans instead of a walk of the whole table (the explain output is in `scripts/load/results/`). The full ten-query review is in PR #303; the other candidate index measured no better and was left out on purpose.
- The care agent's paper trail (issue #302, migration 0017): `agent_proposals` holds one suggestion (kind, title, reason, the payload and the evidence rows the rule used, a status from pending to done/failed, an expiry, and a dedupe key — the same suggestion cannot be open twice for one patient), and `agent_actions` logs every action that ran for a proposal. Patients read their own and doctors their patients'; only the server writes. `decide_proposal(id, approve)` is the one way a patient moves a proposal (their own, pending, unexpired; it stamps `decided_at`), and `expire_proposals()` closes overdue ones from a cron job. On the app side: `listMyProposals`, `decideProposal`, `useMyProposals` and `useDecideProposal`.
- What every AI call costs is now recorded and readable (issue #300): `ai_runs` gains `provider`, `input_tokens`, `output_tokens` and `latency_ms` (migration 0015, filled in by the server as it writes each run; older rows keep no size). A service-role-only view `ai_usage_daily` rolls calls and tokens up per user, per feature, per day in Asia/Kolkata, and `my_ai_usage_today()` hands a signed-in user only their own totals for today — the numbers behind the "AI uses left today" line, through `getMyAiUsageToday` and `useMyAiUsageToday`.
- Plain links to look up a price yourself (`pharmacySearchLinks`, `labSearchLinks`), the e-RaktKosh stock page and WhatsApp / SMS share links in `@vyana/shared`. The app reads no price from these sites; the screens that use them follow in the next releases.
- A condition can no longer be added twice (issue #333): migration 0020 first removes the duplicates already stored (the oldest row of each name stays, and care plans that pointed at a removed row are moved to it, not deleted), then a unique index on the patient and the name — compared without case or the spaces at the ends — keeps them out. Adding or renaming into a duplicate now answers "You already have this condition on your list." instead of the database's error, and the condition list itself shows each name once even on a database that has not had the migration yet. (The live check leaving the duplicates behind is fixed in PR #311.)
- Search engines can now find the public pages: the web app serves a sitemap listing the five public pages (`/`, `/login`, `/signup`, `/privacy`, `/terms`), its own robots rules (the public pages allowed; the signed-in app, `/api/` and the token share pages disallowed), and every public page declares its canonical URL.

### Fixed
- Phone UI bugs from the 1.1.0 screen walk (#332): the Ask Vyana header takes the same side margin as every other tab (a non-scrolling `Screen` rendered its header outside the padded container, which also fixes the Timeline title); assistant answers render their Markdown (headings, bold, italics, lists, links) through a phone `FormattedMarkdown` over a tested parser in `@vyana/shared`, and the "Searching trusted sources…" pill shows once and only while a search is running; the HbA1c bars take the colour of each report's own flag (calm warning for "above range", strong red only for "low"), date labels are short ("20 Oct") and value labels skip every second bar when crowded so nothing touches; the triage age placeholder fits its field; the "AI-generated" banner no longer appears on screens with no AI text (Daily Meal Log, PM-JAY, Prescription Basket, Compare Lab Prices); the caregiver invite's privacy lines wrap in full (`ListRow` gains `wrapTitle`) instead of cutting consent text with "…"; and pushed screens have one way back — the stack bar is a plain back arrow on the canvas colour with no duplicate title, the in-screen "Done" / "Cancel" back buttons and the detail screens' "Back" pills are gone, and each screen keeps its one large title.
- A price check (basket or labs) no longer gives up on a pharmacy or lab whose agent waited a long time in the queue and then started: the queue deadline now counts only the wait, and a run that has started is timed by its own deadline from when it started (before, a job older than the queue deadline had every still-running agent cancelled and shown as "timeout", however recently it had started).
- The refill date worked out for a prescription item (`computeItemRefill` in `@vyana/shared`) is now the local calendar date: the date was built as a local midnight and then read back through UTC, so in India it came out one day early (a pack starting 1 Oct, twice a day, 30 tablets said 15 Oct instead of 16 Oct).
- The trend helper now decides its direction (up, down or about the same) from the unrounded change: a change just under a flat limit (for example 499.96 steps against a 500 limit) used to round up onto the limit and report as a rise or fall; the rounded number is unchanged and is used only for the words.
- The Docker image now pins musl to 1.2.6-r3, the version that fixes CVE-2026-107891, until the base image ships it.
- The Medical ID QR now always fits its 400-byte limit: after the medicines and the allergies have been given up, a still-too-long payload shortens the emergency contact's name a character at a time, then the patient's name — a long name in a three-byte script such as Devanagari could pass the cap on its own (up to 515 bytes before, denser than a phone camera reads reliably). The blood group and the contact's phone number always stay whole.
- Android app: the next APK no longer asks for the microphone or for "draw over other apps" (issue #377). The 1.0.0 APK requested `RECORD_AUDIO` and `SYSTEM_ALERT_WINDOW`, which the app never uses: the image picker plugin added the microphone permission by default (the app only ever picks images), and the overlay permission arrived through a library manifest merge. The picker is now told `microphonePermission: false`, both permissions stay in `android.blockedPermissions`, a check (`apps/mobile/scripts/check-android-permissions.mjs`) fails if either stops being blocked in the generated manifest, and `apps/mobile/BUILD.md` makes dumping the built APK's permissions a required step before it is published.
- Safari no longer logs a console error on every page load: the `interactive-widget` viewport key (#245) is kept out of the static viewport meta tag — WebKit does not know the key — and `KeyboardGuard` adds it at runtime only in Chromium, the one engine that understands it (issue #362).
- The care plan gets the guidance of a MedlinePlus page, not its menu: the "On this page" list and the lists of outside links are dropped, and the model sees the first page (the best matching topic) up to 5,500 characters and the others up to 2,500, so treatments and prevention are on what it reads (before, the first 3,500 characters were menu, risks and symptoms and every bullet was dropped).
- The care plan works with the new page reader: the text of a page is now taken from its main content (`<main>` or `<article>`), not from the menus and banners at the top (the model used to get 3,500 characters of navigation and every bullet was dropped, so the care plan answered 502), and common HTML entities such as `&rarr;` are decoded.
- Wording that claimed more than the app does: the consent text said identifying details are removed "before any AI analysis", but a photo is first read by a vision model that sees the whole image (the details are removed from the text after that); the SOS screen called Blinkit Ambulance a "rapid dispatch partner", but Vyana has no partnership (now "also available, not run by Vyana").
- Accessibility pass (U1): no text under 11 px/pt anywhere — the phone tab bar labels (web and phone), the doctor pages' small badges and the phone's report and prescription details all move to 11. Tap targets that were 36 px are now 44: the header sign-out button, the sheet close button and the small icon button. On the phone, the secondary and tertiary text colours are aligned with the web tokens (label2 0.78, label3 0.74 opacity), because at the old values they measured 4.50:1 and 3.31:1 on the canvas — under the 4.5:1 that small text needs; they now measure 5.29:1 and 4.75:1.
- Accessibility: every input in the doctor's care-plan editor and prescription editor now has a label a screen reader can read — the care plan's add-item boxes were named only by their placeholder text, and the prescription's medicine labels were not tied to their boxes — and keyboard focus is visible on every input: both editors now use the design system's focus border, and the care plan's inline edit boxes, whose focus outline was removed with nothing in its place, show the standard focus outline again.
- Doctor check follow-ups (issue #359): an admin's approval stores the registration number and state council exactly as the admin typed them (no trimming on the admin side; matching still compares the normalised forms), and the doctor verify route settles the caller's role before reading the body, so a patient or caregiver always gets 403, even with a body that is not JSON. The keep-verified comparison now covers the registration year too (issue #344, as amended): a verified doctor who changes any one of number, council or year goes back to pending with `verified_at` cleared, and only all three unchanged keeps `verified`.

### Changed
- Route and error-shape alignment (issue #374): the account-deletion answer is built from its `OkRes` contract like every other route; correcting a lab value is now rate-limited with the report group (`ai_document`, 10 an hour) and declares its time limit; the share page's 404 is built by the shared error response, keeping its no-store headers; the role checks for the care plan, doctor verify and interaction check sit in their routes like the others (and triage records in a comment why it has none); a report's language is settled in the report service, not the route; the e-RaktKosh reader logs and returns nothing when the source does not answer, like the other sources, and a failed file cleanup during account deletion is an upstream error instead of a plain one.
- The doctor side of the web app (OPD queue, patient summary, prescription writer and care plan review), onboarding and the consent screen now use the same design system as the patient side — white cards on the grey page, the shared buttons, fields and status pills, teal only for the primary action — instead of the older slate and teal styling. What the pages do has not changed.
- Internals (issue #375): the assistant chat request body now lives in the shared API contracts like every other route — its message cap (4,000 characters) and message roles are declared in the schema, and the OpenAPI reference shows the body — and the PM-JAY hospital search now checks its coordinates against the same bounds as the emergency routes, so an out-of-range latitude or longitude is a 400 instead of a search. The duplicated LLM field helper, the medicine form/frequency/food lists and the ISO-date check each have one home now (the lists are the `PrescriptionItem` contract's own enums). No change for any valid request.
- The live check (`pnpm live:check`) no longer runs the agent routes: the basket job, the lab compare job and the NMC check are gone, and so is the `--agents` flag (the web agent behind them is removed, ADR-072). The blood check now wants the public stock service to answer in under 5 seconds with at least one bank listed, and it skips — instead of failing — when that service does not answer at all. And it cleans up after itself (#333): the care plan check deletes the condition it added (its care plans go with it) and the assistant check deletes the chat session it started, even when the check fails — repeated runs used to leave another "Type 2 Diabetes" and another chat session on the demo patient every time.
- RapidBlood screens match the faster search: the per-area progress and the "2 to 3 minutes" text are gone from the web `/blood` page and the phone's blood screen — a short skeleton shows while the source page is read (about a second now). Bank rows are sorted by units listed, then by the freshest read (`sortBloodBanks` in `@vyana/shared`), each row shows the update written on the source row and a "Call to confirm" line. When a search finds nothing or cannot be read, the card offers "Open e-RaktKosh" and "Share this request" on WhatsApp or by SMS; the same WhatsApp and SMS buttons now sit on every request card on web and phone (the phone's native Share button is gone).
- Medicine prices are looked up, not checked: the web `/basket` page and the phone basket are now "Compare medicine prices" — tap a medicine and four buttons ("Search on Tata 1mg / PharmEasy / Netmeds / Apollo Pharmacy") open the shop's own search page, with a free field for any other medicine and the plain line "Prices are on the shop's own page. Vyana does not show or check prices." The phone's lab screen works the same way with `labSearchLinks` ("Open Healthians" for a lab without a search page, no city to pick), each test on the web report page carries the same lab links, and the Meds tab's single-medicine card opens the four pharmacy searches directly. No screen starts or polls a basket or labs job any more.
- Every AI call now records its provider, token counts and duration.
- Nearby hospitals (the SOS screen and `/api/emergency/nearby`) come from OpenStreetMap through one request to the public Overpass service (about a second; before: about 66 seconds with a web agent and an AI model), with the seeded hospitals table as the fallback within 60 km. The emergency and ICU fields are only set when the map says so (emergency "yes"); a hospital the map does not describe shows neither, never a "no".
- Doctor registration is checked by an admin by hand: the doctor sends the details, the admin approves or rejects; no automatic register lookup any more.
- Care plan pages, the assistant's trusted links and the medicine interaction check no longer use the web agent vendor. The care plan finds its pages with the MedlinePlus topic search and reads them with an own page fetch (allow-listed sites only, https only, redirects checked, cached a day); the assistant searches MedlinePlus the same way, and its price tool became links to the pharmacies (it never states a price). The interaction check uses only the reviewed table: a pair the table does not cover is listed as not checked, never as "no interaction".
- RapidBlood reads the stock directly from the public e-RaktKosh service instead of a web agent: results come in about a second (before: 2 to 3 minutes), the city is matched to a district of the source (Gurugram and Noida work too), rows with several blood groups in one cell or without a count are not shown, answers are cached for 15 minutes and requests carry an identifying User-Agent. The wording stays: "listed", call to confirm. Blood search has its own rate-limit bucket (20 per 10 minutes).
- The basket, lab and blood job pollers now share one helper for opening a job and polling an agent run (before, the flow was copied per poller and the copies had drifted and taken the same bug twice). No behaviour changes; the one deliberate difference is written at the helper: a run's deadline is chosen per job — the basket's grows with the number of medicines, labs keep the flat 190 seconds for a single-task run.
- Dead code removed (issue #376): the unused `upstreamTimeout` error helper, the duplicated `BLOOD_GROUPS` / `BLOOD_COMPONENTS` lists in `@vyana/shared` (the contract enums are the one source now), a care-plan re-export nobody imported, and fifteen `lib/server` helpers that only their own file used are no longer exported.
- The Android app no longer takes part in Google cloud backup or device-to-device transfer (`allowBackup` is set to false in the Expo config): the local data on the phone — cached health data and app state — stays on the device it was created on instead of travelling with a Google account backup.

### Fixed
- Chat history stays in step between the phone and the web: a chat started on one device is listed on the other when the assistant opens (the history is no longer kept for 5 minutes without a check), the saved chat is read again after every reply, and on the phone the first reply of a new chat no longer disappears (the guard the web already had).
- A care plan no longer fails with a server error when the first model rejects its long answer (Groq `400 json_validate_failed`): the next model in the pool is tried. Every error that stops the model pool is now logged with its status and code.
- When a model rejects its answer, the pool skips that model's other keys and goes straight to the next model, and the log line carries the provider's short reason.
- The care plan works again on the free Groq tier: the model gets the first 3,500 characters of each guideline page instead of 12,000, because prompt and answer together must fit 8,000 tokens a minute (before, every answer was cut short and the request ended in a timeout).

## [1.1.0] - 2026-10-22

### Added
- On the dashboard, the name of a chronic care plan is a link to that plan (`/care/<condition>`), so a patient can reach the full plan and generate one for a condition they added themselves.
- Health Memory Graph page (issue #238): the public share page now draws the memory a scoped link carries (data from #237). The page is split into `components/share/*`: a header card with the patient's name, age, blood group and allergies and a live expiry countdown; the record's events on one timeline; lab trends with the stored reference range as a shaded band and each point coloured by its stored flag; vitals as lines, blood pressure with both numbers; medicines as bars over time on one scale; and the last 30 days of doses as a strip of day squares with the taken percentage. A sticky mini-nav jumps between the sections the link actually has, the charts are hand-made SVG, and a print stylesheet keeps only the record on paper.
- Android app (issue #236): Find blood — RapidBlood on the phone, the mobile half of the search and tracker (the website has the same page): blood group and city come from the profile, progress shows per area while the source pages are read, banks come listed with units, the source link and call and message buttons, and the request tracker's statuses are set by tapping them. Entry points sit on the SOS screen under the Medical ID card and in Profile's quick links, and the standing text — stock is what the source page showed, call to confirm, in an emergency call 108 — stays on screen at all times.
- Android app (issue #239): the Timeline share link is now the patient's choice — how long it lasts (24 hours, 7 days or 30 days) and which parts of the record it includes (labs, vitals, medicines, adherence, from #237; each section is off until the patient switches it on, so a quick share sends the basic timeline only). "Copy link" copies for real (expo-clipboard). Profile's "Active share links" show what each link includes and how often it has been opened ("Opened 3 times, last 2 h ago"), with the same revoke as before.
- Health Memory Graph data (issue #237): a share link can carry scopes (labs, vitals, medicines, adherence); the shared record then returns a `memory` with only those sections (labs of the last 24 months capped at 24 tests × 24 points, vitals of the last 12 months, medicines over time, adherence of the last 30 days), and every open of a link is counted for the patient (`open_count`, `last_opened_at`, written by the server only). Links without scopes behave exactly as before. The graph page is #238 and the phone side is #239.
- RapidBlood tracker data (issue #235): a `blood_requests` table (owner-only) with the queries and hooks the screens build on, the request message a patient can share, and demo requests for two demo patients. The blood-bank search itself is #234 and the screens are #236.
- The website has a "Download for Android" button (and an "Android app" link in the menu). `/download/android` sends the visitor to the .apk of the latest GitHub release.
- New API shapes for v1.1.0, with fictional mocks and hooks, before the screens exist: `POST /api/blood/search` and `GET /api/blood/search/{job_id}` (blood bank search job; `useSearchBlood`, `useBloodJob`) and `memory` on `GET /api/share/{token}` (the sections a Health Memory Graph link contains; `null` for a link without scopes).
- RapidBlood server: `POST /api/blood/search` starts one web agent per area (your city and up to three nearby cities) on the public e-RaktKosh stock page; `GET /api/blood/search/{job_id}` returns the banks. A row counts as verified only when the copied row text holds the bank name and the unit count; results are cached for 15 minutes. The screens follow.
- RapidBlood on the website (`/blood`): choose a blood group, what is needed and a city, see the blood banks that list stock (with units, the time written on the source page and a link to it, and whether the row matches the page text), call or open the source, then start a request and move it through "Searching, Contacted, Confirmed by the blood bank, Arranged, Received, Cancelled" yourself, with a message to copy or send on WhatsApp. The same safety text is always on the page. Entries: the SOS page and the dashboard.

### Removed
- Medicine quality alerts (CDSCO): the alerts screen, `POST /api/alerts/check`, the TinyFish Monitor webhook and the `monitor:create` script. The `drug_alerts` and `tinyfish_monitors` tables stay in the database, unused.

### Changed
- Android app: improved welcome splash screen with Liquid Glass elevated card presentation, subtle ambient accent halo, smooth entrance motion with reduced-motion support, tap-to-skip affordance, and Indian flag pill badge (#240).
- Android app: the native glass tab bar is back (issue #241, re-applying #204 on top of current main). All five tabs draw their own large title with the SOS button beside it; Medicines and Reports move onto the shared `Screen`, Ask and Me keep their one title from #229, Today keeps its greeting, and the root keyboard provider is untouched. Needs a real-device pass on Android and iOS before it is marked ready.
- Demo data: ten more fictional demo patients with different diseases and three caregivers, and a year of lab reports, vitals and dose logs for every demo patient (for the charts and the shared record).
- The website no longer offers "Install app" in mobile browsers (the web manifest uses `display: browser`), so visitors do not mistake it for the Android app.
- Android app: the Today screen now greets you by name and time of day ("Good morning, Piyush") instead of showing an alert banner.

### Fixed
- Android app: booking a token and uploading a report now use the phone's own date (before 05:30 in India "today" was yesterday); the caregiver's medicine list no longer shows "1 dose" when the dose is not recorded.
- A missed-dose alert that the push service delivered to nobody is no longer counted as sent: the dose is given back and the next run tries again (before, every failed ticket left the alert marked as done and the caregiver was never told).
- Website: "Ask Vyana" and "Appointments" are in the menu (both pages could only be reached by typing the address), the consent boxes start unticked, the booking page no longer links to a symptom checker page that exists only in the app, the home page and terms no longer promise Jan Aushadhi generics, the care plan sentence on the home page now says what really happens (a plan you generate yourself is marked "Not reviewed by a doctor"), the interaction messages say what was not checked, and the doctor's "Check interactions" sends the patient.
- Android app: SOS no longer says an ambulance was dispatched or shows an arrival time that was made up: it says the request is saved and to call 108; the 108 and 112 buttons say so when the dialer cannot open; the caregiver's "Call 108 for the patient" button now dials 108 (it used to open the caregiver's own SOS screen); a profile without a blood group stays empty instead of being saved as B+; the OPD timing lookup on the booking screen is asked once per hospital (it looped); government hospitals show GOVT; "Copy link" on the Medical ID copies the link; a refill estimate that is not known no longer reads "~null days"; the app keeps its light look when the phone is in dark mode, and no longer asks for the microphone or "draw over other apps".
- The phone's share link list no longer fails on a link that has no scopes or open count yet (a database that is a step behind the app).
- Booking flow (issue #223): the hospital list could come back empty on the first visit after signing in and then stay empty until a full reload. The hospitals and departments tables are readable by signed-in users only, so a read that reached the database before the browser client had attached the user's token looked exactly like "no hospitals" — a success with no rows, which the query cache kept. The hospital hooks now wait for the client's own session before reading, and the empty states on the booking page offer a retry instead of a dead end.
- **Assistant markdown formatting (QA #221):** Chat answers on `/assistant` now render formatted Markdown (bold, italic, inline code, headings, bulleted/numbered lists, and tables) instead of showing raw Markdown syntax.
- **Heading hierarchy (QA):** Section 3 of Terms of Service and Essential Medical Disclaimer on Privacy Policy now use an h2 matching sibling numbered sections, "On this page" uses sentence-case text, and Third-Party Data Processors on the Privacy Policy uses title-case h3 matching standard heading hierarchy for consistent screen-reader navigation (#219).
